# ADR-0004 回复限流与 token 预算分离

- 状态：Proposed
- 日期：2026-10-24
- 决策者：待确认
- 关联接口：`IF-LIM-001`、`IF-BUD-001`

## 背景

当前 `AIRequestLimiter` 同时承担会话冷却、每分钟调用上限和每日调用上限，并在内存中记录 token 用量。

用户计划后续增加中转站，按每日 token 总额度（例如一千万）硬切断，并允许 Agent 查询剩余额度。如果把“防刷屏”和“控成本”继续放在同一个组件里，后续替换中转站会互相干扰。

## 决策

拆成两个独立职责：

- `ReplyThrottle`：会话冷却、每分钟次数、每日调用次数、防自循环。继续使用现有 `AIRequestLimiter` 语义。
- `BudgetProvider`：每日 token 上限、已用、剩余、重置时间、额度快照。

当前阶段：

- 保留现有冷却和频率限制。
- 暂不硬切断 token 用量。
- 先本地记账，后续由中转站作为权威来源。
- `QUOTA_EXHAUSTED` 禁止自动重试。
- 群聊额度耗尽默认沉默，私聊是否提示由配置决定。

## 后果

正面：

- 防刷屏和控成本互不干扰。
- 中转站可以独立演进。
- Agent 可以查询余额而不修改额度。

负面：

- 多一个组件和配置面。
- 本地预检查不能保证多实例绝对不超，需要中转站原子裁决。
- 需要区分调用次数和 token 用量的统计口径。

## 替代方案

- 一个限流器同时管次数和 token：实现简单，但职责混乱，难以接中转站。
- 只靠供应商侧限额：无法做本地冷却和余额查询。

## 迁移与验收

- 保留 `AIRequestLimiter` 现有测试。
- 新增 `BudgetProvider` 契约测试。
- 模拟 `QUOTA_EXHAUSTED`，验证不调用模型、不重试。
- 验证 `/status` 和 `get_budget_status` 返回一致的额度快照。
