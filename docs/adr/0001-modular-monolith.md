# ADR-0001 模块化单体与端口/适配器

- 状态：Accepted
- 日期：2026-10-24
- 决策者：项目维护者
- 关联接口：`IF-DOM-001`、`IF-APP-001`、`IF-LLM-001`、`IF-MSG-001`、`IF-CTX-001`

## 背景

项目需要同时接入 QQ、未来其他社交平台、不同模型供应商、记忆、审计、预算和管理后台。当前是单人开发、本地部署、低并发场景。

如果直接在 NoneBot 插件中写业务逻辑，平台 SDK、模型 SDK 和数据库会互相耦合，后续增加平台或替换模型时成本很高。

如果一开始拆微服务，会引入部署、网络、服务发现、分布式事务和可观测性成本，超过当前需求。

## 决策

采用模块化单体：

- 单进程部署。
- 领域、端口、应用、基础设施、启动装配、平台插件分层。
- 外部 SDK 只出现在基础设施和插件层。
- 应用层依赖端口，不依赖具体 SQLite、DeepSeek 或 NoneBot。
- 通过 `AppContainer` 集中装配。
- 通过测试检查核心层不导入平台/供应商 SDK。

不采用微服务，不引入消息队列，不引入分布式锁。

## 后果

正面：

- 部署简单，调试成本低。
- 平台、模型和存储可以替换。
- 测试可以使用 Fake LLM 和内存仓储。
- 后续可以在边界清晰后拆出连接器或 worker。

负面：

- 单进程是单点故障。
- 应用层当前仍依赖 `bootstrap.config.Settings`，需要后续收敛。
- 模块边界需要人工和测试持续维护。

## 替代方案

- 直接在 NoneBot 插件中写全部逻辑：开发快，但不可扩展。
- 一开始微服务化：隔离强，但当前收益不足以抵消复杂度。

## 迁移与验收

- 保持现有分层目录。
- 逐步消除 `application -> bootstrap` 的具体配置依赖。
- 增加导入边界检查。
- 在出现第二个平台连接器或后台任务明显影响回复延迟时，再评估拆分 worker。
